우리가 "터미널"이라고 부르는 건 프로그램 하나가 아니라 **네 층이 안으로 겹친 구조**다. 바깥 층은 화면을 맡고, 안쪽으로 갈수록 실제 일을 한다.

## 한눈에 보기

```
┌─ 1층 터미널 에뮬레이터 ─────────────────────────────────┐
│  iTerm2 · Warp · Ghostty                                │
│  ┌─ 2층 멀티플렉서 (없어도 됨) ──────────────────────┐  │
│  │  tmux · herdr · Zellij                            │  │
│  │  ┌─ 3층 셸 ────────────────────────────────────┐  │  │
│  │  │  zsh · bash · fish                          │  │  │
│  │  │  ┌─ 4층 실제 프로그램 ───────────────────┐  │  │  │
│  │  │  │  ls · git · vim · python · Mdir.js    │  │  │  │
│  │  │  └───────────────────────────────────────┘  │  │  │
│  │  └─────────────────────────────────────────────┘  │  │
│  └───────────────────────────────────────────────────┘  │
└─────────────────────────────────────────────────────────┘
```

각 층은 바로 옆 층하고만 대화한다. 그래서 한 층을 바꿔도 나머지는 그대로 쓸 수 있다.

| 층 | 이름 | 예시 | 하는 일 | 비유 |
| --- | --- | --- | --- | --- |
| 1 | 터미널 에뮬레이터 | iTerm2, Warp, Ghostty | 창을 띄우고, 키를 받고, 글자를 그림 | TV 화면과 리모컨 |
| 2 | 멀티플렉서 (선택) | tmux, herdr, Zellij | 화면 분할, 세션 유지 | 화면 분할 + 이어 보기 기능 |
| 3 | 셸 | zsh, bash, fish | 명령을 해석하고 프로그램을 실행 | 안내 데스크 직원 |
| 4 | 실제 프로그램 | ls, git, vim, python | 진짜 일을 함 | 실제 업무를 하는 부서 |

## 1층: 터미널 에뮬레이터 (iTerm2, Warp)

에뮬레이터는 화면과 키보드를 담당하는 "창" 프로그램이다. 명령어가 무슨 뜻인지는 전혀 모른다.

옛날에는 터미널이 컴퓨터에 연결된 실제 기계(모니터와 키보드)였다. 지금 쓰는 터미널 앱은 그 기계를 소프트웨어로 흉내 낸 거라 "에뮬레이터"라고 부른다.

**하는 일**

- 창, 탭, 폰트, 색상 테마를 관리한다.
- 누른 키를 안쪽 층으로 그대로 전달한다. `ls` 를 쳐도 에뮬레이터 입장에서는 'l', 's', 엔터를 보낼 뿐이다.
- 안쪽에서 돌아온 글자와 제어 코드를 해석해서 화면에 그린다. 제어 코드(ANSI 이스케이프 코드)는 "여기부터 빨간색", "커서를 위로", "화면 지우기" 같은 명령이다.
- PTY(가상 터미널)를 만들어 안쪽 프로그램과 연결한다. PTY 는 층과 층을 잇는 가상의 케이블이다.

**Warp 는 뭐가 다른가?** Warp 도 에뮬레이터다. 입력창을 텍스트 에디터처럼 만들고, 명령과 결과를 "블록"으로 묶고, AI 기능을 더했다. 명령을 실제로 실행하는 건 여전히 안쪽의 zsh 나 bash 다.

## 2층: 멀티플렉서 (tmux, herdr)

멀티플렉서는 없어도 되는 층이다. 한 창을 여러 칸으로 나누고, 창을 닫아도 안의 작업이 계속 살아 있게 해 준다.

**하는 일**

- **화면 분할**: 한 창을 여러 패널로 나누고, 패널마다 셸을 하나씩 띄운다.
- **세션 유지**: 창을 닫거나 SSH 연결이 끊겨도 안의 프로그램은 계속 돌아간다. 다시 붙으면(attach) 하던 화면 그대로 이어진다. 원격 서버에서 작업할 때 특히 유용하다.

**"터미널 안의 터미널"**: 멀티플렉서는 패널마다 작은 에뮬레이터를 하나씩 품고 있다. 안쪽 프로그램의 출력을 직접 해석해서 자기 화면을 다시 그리고, 그 결과를 바깥 에뮬레이터에 보낸다.

**iTerm2 의 분할 기능과 차이**: iTerm2 에서 나눈 창은 앱을 닫으면 사라진다. tmux 세션은 따로 떠 있는 서버 프로그램이라 앱을 닫아도 남아 있다.

**herdr**: tmux 같은 멀티플렉서에 AI 코딩 에이전트의 상태(작업 중, 막힘, 완료)를 보여 주는 기능을 더한 도구다.

## 3층: 셸 (zsh, bash)

에뮬레이터가 화면을 담당한다면, 셸은 명령을 담당한다. 입력한 줄을 읽고 어떤 프로그램을 어떻게 실행할지 정한다.

**하는 일**

1. 프롬프트(`~ %` 같은 표시)를 출력하고 입력을 기다린다.
2. 입력한 줄을 해석한다. 예를 들어 `ls -l | grep txt` 는 "ls 와 grep 두 프로그램을 실행하고, 앞의 출력을 뒤의 입력으로 연결하라"는 뜻이다.
3. 프로그램을 실행하고, 끝날 때까지 기다렸다가 다시 프롬프트를 띄운다.
4. 변수, 별칭(alias), 자동완성, 명령 히스토리, 스크립트 실행을 처리한다.

셸은 화면을 직접 그리지 않는다. 글자를 내보낼 뿐이고, 그걸 화면에 그리는 건 에뮬레이터다.

맥의 기본 셸은 zsh 다. 층이 나뉘어 있어서, iTerm2 에서 Warp 로 바꿔도 셸 설정 파일(`.zshrc`)은 그대로 적용된다.

셸은 네 층 중 사용자가 가장 많이 "말을 거는" 층이라 조금 더 들여다본다. 아래 소절은 [Bash 매뉴얼](https://www.gnu.org/software/bash/manual/bash.html)과 [zsh 문서](https://zsh.sourceforge.io/Doc/Release/Files.html)를 참고해 정리했다.

### 셸도 그냥 프로그램이다

셸은 운영체제의 특별한 일부가 아니라 `/bin/zsh` 같은 평범한 실행 파일이다. 에뮬레이터(또는 멀티플렉서)가 PTY 를 만든 뒤 그 안쪽에 처음 띄워 주는 프로그램이 셸일 뿐이다. 지금 어떤 셸이 기본으로 지정돼 있는지는 이렇게 확인한다.

```bash
echo $SHELL   # /bin/zsh
```

macOS 는 Catalina 부터 [기본 셸이 zsh](https://support.apple.com/en-us/102360) 다.

### 한 줄이 실행되기까지

엔터를 누르면 셸은 그 줄을 곧바로 실행하지 않고 여러 단계를 거친다. Bash 매뉴얼의 [Shell Operation](https://www.gnu.org/software/bash/manual/bash.html#Shell-Operation) 이 정리한 순서는 이렇다.

1. 입력을 단어와 연산자(`|`, `>`, `&&` 등)로 쪼갠다. 이때 따옴표 규칙이 적용되고 alias 가 펼쳐진다.
2. 쪼갠 토큰을 단순 명령과 복합 명령(파이프라인, `if`, `for` 등)으로 파싱한다.
3. [확장(expansion)](https://www.gnu.org/software/bash/manual/bash.html#Shell-Expansions)을 수행한다 — 중괄호 `{a,b}`, 틸드 `~`, 변수 `$HOME`, 명령 치환 `$(...)`, 산술 `$((...))`, 단어 분리, 파일 이름 `*.txt` 순이다.
4. 리다이렉션(`>`, `<`)을 처리하고 인자 목록에서 지운다.
5. 명령을 실행한다.
6. 끝나기를 기다려 종료 상태를 거둔다.

중요한 건 **확장이 실행보다 먼저**라는 점이다.

```bash
ls ~/*.txt
# ls 가 실제로 받는 인자: /Users/me/a.txt /Users/me/b.txt
```

`ls` 는 `~` 도 `*` 도 본 적이 없다. 셸이 이미 파일 이름 목록으로 바꿔서 넘겼기 때문이다. 따옴표는 이 확장을 막는 장치다 — 작은따옴표 안에서는 아무것도 확장되지 않고, 큰따옴표 안에서는 `$변수` 와 `$(...)` 는 확장되지만 `*` 와 단어 분리는 일어나지 않는다.

```bash
echo '$HOME'   # $HOME
echo "$HOME"   # /Users/me
```

### 내장 명령과 외부 프로그램

셸이 실행하는 명령이 전부 4층의 프로그램인 건 아니다. `cd`, `export`, `alias` 같은 명령은 셸 안에 들어 있는 **내장 명령(builtin)** 이다.

```bash
type cd   # cd is a shell builtin
type ls   # ls is /bin/ls
```

`cd` 가 내장인 데는 이유가 있다. 외부 프로그램은 셸의 자식 프로세스로 실행되는데, 자식이 자기 작업 디렉터리를 바꿔 봐야 부모인 셸의 디렉터리는 바뀌지 않는다. 셸 자신의 상태를 바꾸는 명령은 셸 안에서 실행돼야 한다.

내장도 함수도 아닌 이름은 `$PATH` 에 적힌 디렉터리를 앞에서부터 뒤져 실행 파일을 찾고, 새 프로세스를 만들어 실행한다([Command Search and Execution](https://www.gnu.org/software/bash/manual/bash.html#Command-Search-and-Execution)). "command not found" 는 이 탐색이 실패했다는 뜻이다.

### 파이프와 리다이렉션

프로그램은 표준 입력(0), 표준 출력(1), 표준 에러(2) 세 통로를 갖고 시작한다. 이 통로가 어디에 연결될지는 프로그램이 아니라 **셸이 실행 전에 정한다**([Redirections](https://www.gnu.org/software/bash/manual/bash.html#Redirections)).

```bash
ls > files.txt        # 표준 출력을 파일로
ls nope 2> err.txt    # 표준 에러를 파일로
sort < files.txt      # 파일을 표준 입력으로
ls -l | grep txt      # ls 의 표준 출력을 grep 의 표준 입력으로
```

`ls` 는 자기 출력이 화면으로 가는지 파일로 가는지 파이프로 가는지 신경 쓰지 않고 표준 출력에 쓸 뿐이다. 작은 프로그램을 이어 붙일 수 있는 건 이 연결을 셸이 맡아 주기 때문이다.

### 종료 상태

모든 명령은 끝나면서 숫자 하나를 남긴다. 0 이면 성공, 그 외는 실패다([Exit Status](https://www.gnu.org/software/bash/manual/bash.html#Exit-Status)). 직전 명령의 값은 `$?` 에 들어 있고, `&&` 와 `||` 는 이 값을 보고 다음 명령을 실행할지 정한다.

```bash
ls nope; echo $?           # 0 이 아닌 값
pnpm build && pnpm deploy  # build 가 성공했을 때만 deploy
cd app || exit 1           # cd 가 실패하면 종료
```

### 셸 변수와 환경 변수

`NAME=value` 로 만든 변수는 그 셸 안에서만 보인다. `export` 를 붙여야 **환경 변수**가 되어 셸이 실행하는 자식 프로그램에 전달된다.

```bash
A=1
export B=2
node -e 'console.log(process.env.A, process.env.B)'   # undefined 2
```

전달은 부모에서 자식으로, 복사로만 일어난다. 스크립트를 그냥 실행해서는 그 안의 `export` 가 지금 셸에 남지 않고, 지금 셸에서 읽어 들이는 `source` 를 써야 남는 이유다.

### 작업 제어

셸은 실행한 프로그램을 **작업(job)** 으로 관리한다([Job Control](https://www.gnu.org/software/bash/manual/bash.html#Job-Control-Basics)).

```bash
pnpm dev &   # 백그라운드로 실행
jobs         # 작업 목록
fg %1        # 1번 작업을 포그라운드로
```

Ctrl+Z 는 포그라운드 작업을 멈추고 셸 프롬프트로 돌아오게 하며, `bg` 로 백그라운드에서 이어 돌리거나 `fg` 로 다시 가져올 수 있다. Ctrl+C 도 셸이 프로그램을 죽이는 게 아니다. 터미널(PTY)이 지금 포그라운드인 작업에 인터럽트 신호를 보내는 것이고, 어느 작업이 포그라운드인지를 정해 두는 쪽이 셸이다.

### 설정 파일은 언제 읽히나

셸은 시작할 때 설정 파일을 읽는데, 어떤 파일을 읽을지는 셸이 어떻게 시작됐는지에 따라 다르다.

| 셸 | 파일 | 읽히는 때 |
| --- | --- | --- |
| zsh | `~/.zshenv` | 항상 |
| zsh | `~/.zprofile` | 로그인 셸 |
| zsh | `~/.zshrc` | 대화형 셸 |
| zsh | `~/.zlogin` | 로그인 셸 (`.zshrc` 뒤) |
| bash | `~/.bash_profile` | 로그인 셸 (없으면 `~/.bash_login`, `~/.profile` 순) |
| bash | `~/.bashrc` | 로그인이 아닌 대화형 셸 |

출처는 zsh 의 [Startup/Shutdown Files](https://zsh.sourceforge.io/Doc/Release/Files.html) 와 Bash 의 [Bash Startup Files](https://www.gnu.org/software/bash/manual/bash.html#Bash-Startup-Files) 다. alias 와 프롬프트처럼 사람이 직접 쓸 때만 필요한 설정은 `.zshrc` 에, 스크립트에서도 보여야 하는 환경 변수는 `.zshenv` 에 두는 식으로 나눈다.

### 대화형 셸과 스크립트

프롬프트에 치는 것과 파일에 적어 실행하는 것은 같은 언어다. 스크립트는 첫 줄의 `#!` 로 어떤 셸이 해석할지를 정한다.

```bash
#!/bin/bash
for f in *.txt; do
  echo "$f"
done
```

그래서 대화형으로 쓰는 셸과 스크립트를 돌리는 셸은 달라도 된다. fish 는 [문법이 bash 와 호환되지 않게 설계](https://fishshell.com/docs/current/fish_for_bash_users.html)됐지만, fish 를 쓰면서 `#!/bin/bash` 스크립트를 실행하는 데는 문제가 없다.

## 4층: 실제 프로그램

셸이 실행해 주는 모든 것이 여기에 속한다. ls, git, python, vim, htop, Claude Code, Mdir.js 모두 4층이다.

크게 두 종류가 있다.

- **출력하고 끝나는 프로그램**: `ls`, `git status` 처럼 결과를 몇 줄 출력하고 바로 끝난다.
- **화면 전체를 쓰는 TUI 프로그램**: vim, htop, Mdir.js, yazi 처럼 커서 이동 코드로 화면을 직접 구성한다. 그 코드를 해석해 그려 주는 건 역시 에뮬레이터다.

프로그램이 실행되는 동안에는 키 입력이 셸이 아니라 그 프로그램으로 간다. 프로그램이 끝나면 다시 셸 프롬프트로 돌아온다.

## 키 하나를 눌렀을 때 일어나는 일

입력은 바깥에서 안으로, 출력은 안에서 바깥으로 흐르고, 층과 층 사이는 PTY 가 이어 준다. tmux 를 켜 둔 iTerm2 에서 `ls` 를 치고 엔터를 누르는 경우를 예로 들면 이렇게 흐른다.

1. **iTerm2** 가 키보드 입력 'l', 's', 엔터를 받아 PTY 로 tmux 에 보낸다.
2. **tmux** 가 지금 선택된 패널을 확인하고, 그 패널의 PTY 로 zsh 에 전달한다.
3. **zsh** 가 `ls` 를 해석하고 ls 프로그램을 실행한다.
4. **ls** 가 파일 목록을 글자와 색상 코드로 출력하고 끝난다.
5. 출력은 거꾸로 올라간다. tmux 가 패널 화면을 갱신해 iTerm2 로 보내고, iTerm2 가 폰트로 그려서 모니터에 표시한다.
6. **zsh** 가 다시 프롬프트를 띄우고 다음 입력을 기다린다.

멀티플렉서를 안 쓰면 2번과 5번의 tmux 단계만 빠지고, iTerm2 와 zsh 가 직접 연결된다.

## 자주 헷갈리는 점

**터미널 앱을 바꾸면 명령어도 달라지나?** 아니다. 명령어는 셸이 담당한다. iTerm2 에서 Warp 로 바꿔도 셸이 zsh 이면 똑같이 동작한다.

**셸을 바꾸면?** zsh 에서 fish 로 바꾸면 문법과 자동완성이 달라진다. 창의 모양과 폰트는 그대로다.

**멀티플렉서는 꼭 있어야 하나?** 아니다. 화면 분할만 필요하면 iTerm2 나 Warp 의 자체 기능으로 충분하다. 원격 서버에서 작업하거나, 창을 닫아도 작업이 이어져야 하거나, AI 에이전트를 여러 개 돌릴 때 쓰면 좋다.

**Mdir 같은 프로그램은 어느 층인가?** 4층의 TUI 프로그램이다. 셸에서 실행되고, 화면은 에뮬레이터가 그려 준다.

**나만의 터미널을 만든다면 어느 층부터 시작해야 하나?** 어느 층을 만들지 고르는 게 출발점이다. 4층 TUI 앱이 가장 쉽고, 그다음이 3층 셸, 2층 멀티플렉서 순이며, 1층 에뮬레이터가 가장 어렵다.

## 정리

- "터미널"은 에뮬레이터 → 멀티플렉서(선택) → 셸 → 프로그램 네 층이 겹친 구조다. 바깥은 화면을, 안쪽은 실제 일을 맡는다
- 에뮬레이터는 키를 전달하고 글자를 그릴 뿐 명령의 뜻을 모른다. 명령을 해석하고 프로그램을 실행하는 건 셸이다
- 셸은 한 줄을 쪼개고, 확장하고, 입출력을 연결한 뒤에야 프로그램을 실행한다. `*` 와 `$HOME` 을 푸는 것도, 파이프를 잇는 것도 프로그램이 아니라 셸이다
- 입력은 바깥에서 안으로, 출력은 안에서 바깥으로 흐르고, 층 사이는 PTY 가 잇는다
- 각 층은 옆 층하고만 대화하므로 한 층만 갈아 끼울 수 있다 — 터미널 앱을 바꿔도 `.zshrc` 는 그대로고, 셸을 바꿔도 창 모양은 그대로다
